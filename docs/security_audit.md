# DSTT セキュリティ監査記録

## 監査範囲

認証・認可、CSRF、リバースプロキシ境界、アップロード上限、保存時暗号化、
機密静的ファイル、HTTP セキュリティヘッダーをコードと自動テストで確認した。

## 確認済みの防御

- 自己登録は既定で無効であり、機密ツールはユーザー・グループ権限で保護される。
- セッション Cookie は本番既定で `Secure`、`HttpOnly`、`SameSite=Lax` となる。
- 保存データ用鍵を環境変数必須にでき、機密ファイルと編集履歴は認証付き暗号で保存できる。
- 状態変更リクエストは Origin / Referer と Fetch Metadata を検査する。
- ログイン失敗上限はDB監査ログを参照するため、複数Gunicornワーカーで共有される。
- 正式なHost名を `DSTT_TRUSTED_HOSTS` で制限できる。
- 個人情報を含む実行時ファイルは `/static/` から直接取得できない。

## 今回修正したリスク

1. **Forwarded ヘッダーの無条件信頼（高）**: 直接到達できる構成では攻撃者が
   クライアント IP、scheme、host を偽装できた。既定の信頼数をゼロにし、信頼する
   リバースプロキシがある場合だけ `DSTT_PROXY_X_FOR`、`DSTT_PROXY_X_PROTO`、
   `DSTT_PROXY_X_HOST` に実際の hop 数を設定する方式へ変更した。
2. **単一リクエスト上限 10 GiB（高）**: メモリ・一時領域を枯渇させる余地が
   大きいため通常の既定を 256 MiB に縮小した。大容量共有はチャンク API を利用する。
   圧縮ツールは既存の合計1GiB仕様を壊さないよう、そのPOSTだけ個別上限を設定する。
3. **ヘッダー欠落時の CSRF 補強（中）**: `Sec-Fetch-Site: cross-site` に加え、
   Origin/Refererが無い `same-site` 要求も拒否し、兄弟サブドメイン経由のCSRFを防いだ。
4. **機密レスポンスのキャッシュ（中）**: 認証済みの画面・APIへ
   `Cache-Control: no-store, private` を付けた。CSS/JS/画像などの静的アセットは除外して
   既存の表示速度とPWAキャッシュを維持し、不要なブラウザ権限も停止した。
5. **固定IDの暗黙的な管理者昇格（高）**: 特定の社員番号だけで管理者と判定・起動時昇格する
   挙動を既定で廃止した。既に DB の `is_admin` が設定された管理者は影響を受けない。移行時に
   限り `DSTT_ENABLE_LEGACY_ADMIN=1` で一時的に永続フラグへ移行できるが、移行後は必ず解除する。
6. **固定CLI署名鍵（高）**: CLIの既知の固定セッション鍵を撤去した。パスワードは会社の
   教育・運用方針を優先し、ユーザビリティを損なわないようソフト側では4文字以上のみ求める。
7. **長期間の認証維持（中）**: Remember Cookie を既定14日、セッション寿命を既定12時間に
   制限した。会社方針に合わせて環境変数でさらに短縮できる。
8. **既知の依存パッケージ脆弱性（高）**: `pip-audit` で検出された aiohttp、
   cryptography、Flask、Pillow、pypdf、pyzipper、requests、Werkzeug を修正版へ更新した。
   2026-08-10時点のPyPI最新版と再照合し、Requests 2.34.2、Werkzeug 3.1.8を採用した。
9. **ログイン防御のワーカー分断（中）**: 従来の遅延処理はプロセスごとだったため、
   DBの失敗監査ログを使う上限判定を追加した。未知ユーザーにもダミーハッシュ検証を行い、
   ユーザー存在の応答時間差と過大な認証入力も抑制した。
10. **継続的検査の欠如（中）**: PR、mainへのpush、週次で `pip-audit` とBanditの
    高重大度検査を実行するGitHub Actionsを追加した。

## 本番導入前の必須設定

- 別々の `DSTT_SECRET_KEY` と `DSTT_DATA_ENCRYPTION_KEY_B64` をシークレット管理基盤から
  投入し、`DSTT_REQUIRE_ENCRYPTION_KEY_ENV=1` として鍵を安全にバックアップする。
- TLS 終端プロキシ以外からアプリポートへ到達できないよう FW で制限し、実構成どおりの
  ProxyFix hop 数だけを設定する。
- `DSTT_SESSION_COOKIE_SECURE=1` と `DSTT_ENABLE_HSTS=1` を明示する。
- 初期管理者は `python create_user.py --admin` で作成し、固定ID互換設定は使わない。
- DB、`instance/`、アップロード、ログ、バックアップをサービスアカウントだけが読める
  権限にし、保存期間を定める。
- WAF / プロキシで接続数・頻度も制限する。アプリ側の同一IP・ユーザーID上限は
  全ワーカーで共有されるが、送信元IPを分散する攻撃への唯一の防御として扱わない。
- 依存パッケージと同梱 Windows バイナリを継続的に SBOM / 脆弱性スキャンへ掛ける。

## 残存リスク

- **社員テーブルの主要項目はSQLite内で平文である。** 編集履歴と一部ファイルには
  アプリケーション暗号化があるが、社員名、住所、生年月日、電話番号などのDB本体は
  SQLCipherではない。今回DB/WAL/SHMをOS所有者だけが読める `0600` に補正し、Web配信領域
  への配置を禁止したが、盗難ディスク・スナップショット対策にはサーバー/クラウド側の
  ボリューム暗号化が必須である。
- 互換性維持のため Origin、Referer、Fetch Metadata がすべて無い非ブラウザ要求を許容する。
  将来は全状態変更へ同期 CSRF トークンを必須化するのが望ましい。
- SQLite は単一ホスト向けである。複数ホスト構成では管理 DB へ移行する。
- `chmod 0600/0700` の自動補正はPOSIX環境向けである。Windowsでは `os.chmod` がNTFS ACLを
  所有者限定にできないため、`instance/`、DB、秘密鍵をサービスアカウント専用フォルダーへ
  置き、管理者がNTFS ACLを設定・監査する。
- 既存運用との互換性を優先して新規・変更パスワードの最低長は4文字に留めている。これは
  強いパスワードポリシーではない。SSO/MFAまたは最低8文字以上への段階移行を別途行う。
- ファイル解析ワーカーの CPU、メモリ、処理時間を OS / コンテナでも制限し隔離する。

## 中規模企業向けサーバーチェックリスト

### ネットワークとTLS

- 公開するのはリバースプロキシの TCP 443 のみとし、SSH は社内VPNまたは踏み台の固定IPに
  制限する。Gunicorn と DB のポートは外部公開しない。
- TLS 1.2/1.3 のみを許可し、自動更新証明書の失効期限を監視する。プロキシからアプリへ渡す
  `X-Forwarded-*` は既存値を破棄して再生成する。
- DNS、クラウド管理画面、GitHub、バックアップ管理にはMFAを必須化する。

### OS・プロセス・秘密情報

- サポート中のOSを自動セキュリティ更新し、DSTTはログイン不可の専用ユーザーで実行する。
  systemd の `NoNewPrivileges`、`PrivateTmp`、書込み可能ディレクトリ制限を有効化する。
- `.env` をWebルートやGitへ置かず、systemd credentialsまたはクラウドのSecrets Managerを使う。
  秘密鍵は少なくとも年1回および漏洩疑い時にローテーションする。
- Gunicorn、画像/PDF処理へメモリ・CPU・実行時間上限を設け、ディスク使用率を監視する。
- SQLiteを使う場合はDBが置かれるボリュームをLUKSまたはクラウドKMSで暗号化する。
  DB、`-wal`、`-shm`、バックアップの所有者がDSTT専用ユーザーで、権限が `0600` であることを
  `stat` で確認する。暗号鍵は同じバックアップや同じアクセス権の場所へ保存しない。

### アカウント・監視・復旧

- 管理者を日常利用アカウントと分離し、四半期ごとに管理者・退職者・ツール権限を棚卸しする。
- リバースプロキシでログイン、共有リンク、アップロードへIP単位のrate limitを設定する。
  連続失敗、管理者操作、権限変更、異常なダウンロード量を通知する。
- DBと暗号鍵を別の保管先へ毎日バックアップし、世代管理・暗号化・削除防止を設定する。
  少なくとも四半期ごとに隔離環境へのリストア訓練を行う。鍵なしバックアップは復元不能である。
- 障害・侵害時の連絡先、隔離、鍵失効、証拠保全、復旧手順を文書化し、年1回訓練する。
